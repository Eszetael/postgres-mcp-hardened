# Independent review, 2026-07-26

Two adversarial passes by a model from a different family (not the one that wrote the code), each
given the actual source of that day's fixes and asked to break them rather than approve them. What
follows is every claim it made, and what happened when the claim was tested. A finding is a
hypothesis until it is reproduced.

## Pass A — defences against hidden characters and parser disagreement

**Claim: homoglyphs bypass the name rules.** A Cyrillic `е` in `setval` is not invisible, not
whitespace, not a format character, so nothing here refuses it — and a name-based rule will not
match it.

*Tested against PostgreSQL 17:* `SELECT sеtval('s',1)` → `ERROR: function sеtval(unknown, integer)
does not exist`. **Not a bypass.** The database resolves identifiers, not appearances; a homoglyph
names a function that is not there. This is the same lesson as the redaction work: the boundary is
what PostgreSQL will do, not what our filter recognises. Deliberately still allowed, with a test
that says so.

**Claim: characters that render as nothing but are not format characters are missed** — Hangul
fillers (U+3164, U+115F, U+1160, U+FFA0), braille blank (U+2800).

*Tested:* they did pass the validator. Against a live database, every one of them also produced
`function does not exist`, so again **not an escape route**. They are refused now anyway, because
the claim we make is that a statement contains nothing a reader cannot see, and one of the readers
we care about is a person looking at the audit log. Refusing them costs nothing.

**Claim: `U&"…"` unicode-escaped identifiers decode to a different name than the validator sees.**
The reviewer talked itself out of this one mid-answer, correctly: PostgreSQL's `U&` prefix applies
to string literals, and `U&"…"` is not identifier syntax there. **No finding.**

**Claim: tokenisation failure returns `Ok(())`, so unlexable input skips the check.** True, and
deliberate — the parser rejects it a moment later with a better message. Worth stating rather than
leaving implicit.

## Pass B — the authorisation gate

**Claim (the important one): the gate and the dispatcher may disagree about what the request is** —
via a non-string `method`, a missing one, duplicate `"method"` keys, case differences, or a batch.

*Tested, eight shapes, against a running server:* every one either required a token or was refused.
Duplicate keys resolve to the same value on both sides — because both read the *same parsed value*,
not the same text twice. That is the architectural reason there is no confused deputy here, and it
is worth writing down: the gate does not re-parse.

**Claim: `required_scope` fell through to `mcp:read` for any name it did not know.** True, and a
test asserted it as correct behaviour, including a literal `anything_added_later`. Comfortable until
the first tool that is more than a read, which would inherit the mildest right in the system with
nobody deciding that. **Fixed:** unknown names now require `mcp:admin`, and a test reads the
published tool list so that adding a tool without classifying it fails the build.

## What the review did not find

No way past the read-only rules. No way to reach data without a token. No divergence between what
is authorised and what is executed.

## Honest limits of this exercise

One reviewer, one sitting, given the code rather than a running server — it could not probe, only
reason. Its two strongest-sounding findings were both wrong in the direction that matters, and only
the database could settle them. Read this as one more pass over ground that nine adversarial rounds
had already covered, not as a clean bill of health.
